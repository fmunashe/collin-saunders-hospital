1Architecture Overview

HMS is a server-rendered monolithic web application built on the Laravel framework with Laravel Nova as the administrative UI layer. It follows a layered MVC-plus-domain architecture, favouring convention, testability, and a small operational footprint suitable for an on-premise hospital deployment.

Architectural style: Modular monolith. All modules share one codebase and database, communicating through Eloquent models and domain events. This keeps the operational surface small while allowing clean module boundaries.

4Application Layers

Presentation

Laravel Nova resources, dashboards, metrics, filters, actions, and the public landing page.

Authorisation

Policies per model + Spatie permissions; report & menu gating via canSee.

Domain

Eloquent models encapsulating business rules through model events (booted hooks) and helper methods.

Services

Report data aggregation, PDF/Excel generation, invoice building.

Persistence

Eloquent ORM over MySQL/PostgreSQL with UUID keys and migrations.

Infrastructure

Redis (cache/queue/session), Horizon workers, filesystem for generated documents.

6Request Lifecycle

Browser → Nginx (TLS) → PHP-FPM → Laravel Kernel → Middleware (auth, Nova guard, CheckNovaRegistration) → Route → Nova Controller / ReportController → Policy authorisation check → Eloquent model (fires domain events) → Database (MySQL/PostgreSQL) → Response (JSON for Nova SPA / PDF stream for reports)

7Background Processing

Long-running or deferrable work (large exports, notifications, scheduled report generation) is dispatched to Redis-backed queues, processed by Laravel Horizon workers under Supervisor.

  • Queue driver: Redis
  • Worker manager: Horizon (auto-balancing, metrics dashboard at /horizon)
  • Process supervision: Supervisor restarts workers on failure/deploy
  • Scheduler: Laravel scheduler via system cron for daily backups, expiry checks, and low-stock alerts

9Data Architecture

  • UUID primary keys across all domain tables.
  • Foreign key constraints with appropriate cascade / null-on-delete behaviour.
  • Indexes on status, date, and foreign-key columns used by reports and filters.
  • Soft deletes on clinical entities (Patient, Visit, Admission, Invoice, Medication, Referral) for recoverability and audit.
  • Immutable ledgers — stock movements and action events are append-only.

10Security Architecture

Transport

TLS 1.2+ enforced at Nginx; HSTS recommended.

Identity

Fortify auth, optional 2FA & passkeys, session encryption.

Access

Policy + permission checks on every resource and report.

Audit

Append-only action-event log of all writes.

Data

Hashed passwords, UUID keys, least-privilege DB user.

App hardening

CSRF protection, input validation, parameterised queries via Eloquent.

11Deployment Topology

The recommended production topology is a single well-specified application server co-located with the database, or a two-node split for higher availability. See the Deployment Guide for full setup.

12Scalability & Resilience

  • Horizontal scaling: stateless app tier (sessions in Redis) allows adding PHP-FPM nodes behind a load balancer.
  • Vertical headroom: the recommended server spec supports 100+ concurrent users with margin.
  • Graceful degradation: queued work retries with backoff; failed jobs are retained for inspection.
  • Backups: nightly database dumps plus filesystem snapshot of generated documents.
  • Zero-downtime deploys: atomic release symlink switch, worker restart via Horizon terminate.
